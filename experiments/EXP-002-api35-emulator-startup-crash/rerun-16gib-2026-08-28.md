# EXP-002 rerun — 16 GiB Lima guest (2026-08-28)

## Purpose

Disambiguate the suspected layer from the original EXP-002. Original run was on
a 3.8 GiB Lima guest that did **not** match the documented `lima-vm.yaml`
(16 GiB + `lima-x11`). Hypothesis under test: the memory deficit contributed to
or caused the QEMU `SIGSEGV` during API 35 boot.

The Lima VM was recreated/provisioned to the documented configuration. This
rerun repeats the original minimal reproduction verbatim.

## Environment (changed vs. original)

- Fedora 44 x86_64 Lima VM, Linux `6.19.10-300.fc44.x86_64`
- **Guest memory: 15.6 GiB** (`MemTotal: 16357676 kB`) — matches `lima-vm.yaml`
- `lima-x11.service` active; `lima-x11 status` exit 0; Xvfb/openbox/x11vnc
  running on `DISPLAY=:99`, VNC `127.0.0.1:5901`
- Nix Android emulator `37.2.6.0` (build `16138043`) — unchanged pin
- API 35 `google_apis` x86_64 system image — unchanged
- `/dev/kvm` readable; `emulator -accel-check` reports KVM version 12 usable
- Repo HEAD `45e936d`

## Reproduction (verbatim from README)

```sh
nix develop -c ./scripts/emulator-start headless   # KVM (-accel auto)
nix develop -c ./scripts/emulator-start software   # TCG (-accel off)
```

Both invocations use `-gpu off -memory 1024 -no-window` as in the original.

## Result — crash reproduces identically

| Mode | Exit | Crash PID | Signal | Core | Unmap warning |
|------|------|-----------|--------|------|---------------|
| headless (KVM) | 1 | 19672 | SIGSEGV (11) | 158.7M present | yes |
| software (TCG) | 1 | 20601 | SIGSEGV (11) | 305.1M present | yes |

`adb -s emulator-5554 get-state` → `device 'emulator-5554' not found`; the
process never reaches `sys.boot_completed=1`.

Both coredumps are `qemu-system-x86_64-headless` from the pinned emulator store
path `/nix/store/1c4zwxyjwrsvrq3rgj3938n57jdh21ga-emulator-37.2.6/...`.

### Exact unmap warning (the smoking gun)

Headless (PID 19672, line 84 of log):

```
WARNING: cannnot unmap ptr 0x7fffcb801000 as it is in the protected range from 0x7fff2b800000 to 0x7fffcba00000
```

Software (PID 20601, line 89 of log):

```
WARNING: cannnot unmap ptr 0x7fffa3e01000 as it is in the protected range from 0x7fff03e00000 to 0x7fffa4000000
```

Pointer addresses differ between runs (ASLR) but the mechanism is identical to
the original 3.8 GiB failure. Log context shows the crash lands during graphics
init: `Graphics backend: gfxstream`, in-guest renderer unsupported →
`lavapipe`/`swangle` fallback (`enableProtectedMemoryEmulation: false`). The
crash occurs **before** Android boot, in the emulator/QEMU startup path, not in
guest code.

## Interim conclusion

The 16 GiB rerun disproves the VM-memory/provisioning hypothesis for the
original `-gpu off` configuration: that configuration still crashes under both
KVM and TCG. It does **not** by itself establish that the protected-range
warning is the crash cause or that gfxstream as a whole is unusable. The
subsequent ANGLE probe below boots successfully while emitting the same warning.

The failure concerns the original emulator renderer selection, not Android
native ABI translation, Chez, or Jolt.

## Renderer-path probe — SwiftShader crashes identically

To distinguish renderer configurations, reran on the 16 GiB VM with
`-gpu swiftshader` (explicitly selecting SwiftShader):

```sh
nix develop -c emulator @jolt_api_35_x86_64 -port 5554 -no-window \
  -no-snapshot -no-snapshot-save -no-boot-anim -noaudio -no-metrics \
  -memory 1024 -accel auto -gpu swiftshader
```

Result: **SIGSEGV again** (PID 22423, core 176.7M retained), with the identical
protected-range unmap warning:

```text
INFO  | Graphics backend: gfxstream
INFO  | emuglConfig_init: vulkan_mode_selected:swiftshader gles_mode_selected:swiftshader
INFO  | initIcdPaths: ICD set to 'swiftshader', using Swiftshader ICD
...
WARNING: cannnot unmap ptr 0x7fffdea01000 as it is in the protected range from 0x7fff3ea00000 to 0x7fffdec00000
```

### Debugger classification (3 configurations, same SwiftShader crash path)

Fedora 44 `gdb` was installed and each retained core was inspected against the
pinned QEMU executable. In every case the faulting thread had an invalid,
unmapped instruction pointer, reached from the bundled
`gles_swiftshader/libGLESv2.so` worker thread:

| Accel | GPU selection | Crash PID | Fault RIP | Renderer caller |
| --- | --- | --- | --- | --- |
| KVM (`-accel auto`) | `off` | 19672 | `0x55555fa97070` | `gles_swiftshader/libGLESv2.so` |
| TCG (`-accel off`) | `off` | 20601 | `0x555561bf5070` | `gles_swiftshader/libGLESv2.so` |
| KVM (`-accel auto`) | `swiftshader` | 22423 | `0x55556bd6f070` | `gles_swiftshader/libGLESv2.so` |

For example, the KVM `-gpu off` backtrace begins:

```text
#0  0x000055555fa97070 in ?? ()
#1  0x00007fffd3cd58fc in ?? () from .../lib64/gles_swiftshader/libGLESv2.so
...
rip 0x55555fa97070
rbp 0x2
```

The RIP falls outside the main QEMU mappings, so this is an invalid control
transfer from the bundled SwiftShader GLES worker, not a symbolized fault in the
QEMU protected-range-unmap code. The warning is correlated with the failures,
but not sufficient to establish causation.

## Working mitigation — ANGLE renderer

Starting the same AVD with `-gpu angle` boots successfully under KVM. The
project script now defaults to this selection and permits an explicit override:

```sh
nix develop -c ./scripts/emulator-start headless
# Override only for a deliberate renderer experiment:
JOLT_ANDROID_EMULATOR_GPU=swiftshader \
  nix develop -c ./scripts/emulator-start headless
```

A clean script-managed KVM boot completed successfully (PID 23815):

```text
Starting jolt_api_35_x86_64 (headless, gpu=angle)
Booted emulator-5554
```

The generated report records KVM usable, API 35, `x86_64`, and ABI list
`x86_64,arm64-v8a`. The emulator remained alive after boot and a 1080×2400 PNG
screenshot was captured. SurfaceFlinger reports the ANGLE/Mesa/llvmpipe
renderer. The same protected-range warning still appears, but boot completes:

```text
WARNING: cannnot unmap ptr ... as it is in the protected range ...
INFO | Boot completed in 19883 ms
```

### Revised diagnosis

This environment has a reproducible failure in the emulator's bundled
SwiftShader GLES execution path, independent of KVM and guest RAM. It has a
working, deterministic KVM workaround using ANGLE. The original renderer crash
is a candidate upstream emulator issue; the successful ANGLE configuration
unblocks API-35 emulator work in this project.

## Deterministic AVD creation and failure guard

The creation branch was exercised with a disposable AVD name and port. The
script invokes `avdmanager create avd` with the pinned x86_64 system image and
an explicit `--path` below `ANDROID_AVD_HOME`; the newly created AVD then booted
through the script under KVM:

```text
Creating AVD jolt_api_35_x86_64_repro with system-images;android-35;google_apis;x86_64
Starting jolt_api_35_x86_64_repro (headless, gpu=angle)
Booted emulator-5556
```

Its generated report records API 35, `x86_64`, ABI list `x86_64,arm64-v8a`, and
KVM version 12 usable. The temporary AVD was stopped and removed after the
probe; the default `jolt_api_35_x86_64` AVD remains intact.

One first disposable creation produced a malformed local `config.ini`: 1,024
NUL bytes replaced the CPU/device block, including `hw.cpu.arch`, and the
emulator failed immediately with `CPU Architecture 'arm' is not supported by
the QEMU2 emulator`. This was not reproduced by a second identical creation,
but it exposed an unbounded `adb wait-for-device` failure mode. The script now
validates both `abi.type=x86_64` and `hw.cpu.arch=x86_64` before launch, and
checks the launched emulator PID while polling boot completion. The malformed
AVD now fails promptly with an actionable error rather than hanging.
